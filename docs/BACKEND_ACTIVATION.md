# External activation

The default APK is an offline playtest. No account or paid subscription is active. All source/configuration layers are included; live deployment needs owner-controlled credentials and consoles.

1. Create/select a Supabase project. Apply the committed CLI-generated `supabase/migrations/*_parent_v07.sql` to an empty application schema; existing deployments need a reviewed migration. CI tests the same SQL with PostgreSQL 17 and auth-role fixtures. Enable email OTP, disable anonymous sign-in, configure SMTP, and include `{{ .Token }}` in the email template. New free projects need custom SMTP to customize templates. Use short JWT lifetimes.
2. Deploy `supabase/functions/parent-api`. The function verifies the bearer via Auth and checks `auth.sessions` on each sensitive call. Supply `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ANDROID_PACKAGE`, `MILO_MONTHLY_PRODUCT`, `MILO_ANNUAL_PRODUCT`, `GOOGLE_SERVICE_ACCOUNT_JSON`, and a base64 32-byte `PURCHASE_ENCRYPTION_KEY` as server environment secrets. Never pass service/signing/encryption keys to Flutter. Back up and rotate the encryption key through an explicit re-encryption migration.
3. Configure the Android application `com.framebynavin.milo` in Google Play, recurring monthly/annual products, service-account Android Publisher access, internal testing and license testers. Complete store-required app/privacy/child-audience declarations. Purchase account binding uses the parent UUID supplied as the store's obfuscated account identifier. The server never trusts a client entitlement claim. Test purchase, restore, cancellation, expiry and account deletion on actual store builds.
4. Publish immutable JSON content packs to HTTPS object storage (R2 or equivalent). Insert reviewed catalogue rows in `content_packs` server-side with version, full JSON SHA-256, tier and published flag. Do not allow clients to write catalogue URLs/hashes. Media is embedded in the bounded JSON, then stored separately on-device; no archive extraction or executable content.
5. Build Flutter with `--dart-define=MILO_SERVICES=live` plus public Supabase URL/key and monthly/annual IDs. Public build values may be passed in an ignored JSON file using `--dart-define-from-file`. `.env.example` describes keys; Flutter does not automatically read dotenv files. The default CI build intentionally uses no live secrets.
6. Provide a stable external signing keystore and ignored `android/key.properties` for release builds. CI debug signing is ephemeral: APKs from separate runs may require uninstall/reinstall and lose local data. Do not uninstall a playtest with valuable creations until you have retained them separately. Production upgrades require the same signing identity. Run `flutter build appbundle --release` with configured signing for Play distribution.

No iOS project/store release is claimed. The store interface is replaceable; this Android release verifies Google Play receipts. No cloud backup is enabled, so there are no child backup uploads to configure. Parent deletion revokes sessions, deletes the account and cascades its records; local creations and Google Play billing are managed separately.

Verified implementation references: [Supabase OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [email-template change](https://supabase.com/changelog/46599-changes-to-email-template-customisation-on-free-tier), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Flutter purchases](https://pub.dev/packages/in_app_purchase/versions/3.2.3), [Google subscription state](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptionsv2). Review current console requirements before production activation.
